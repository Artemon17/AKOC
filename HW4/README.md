# Наконечный Артемий. БПИ 253.

Консольное приложение на C для имитации обнаружения и тушения лесного пожара. Модель дискретная, тактовая. В одном процессе выполняется симуляция мира, а при включении сетевого режима события передаются подключённым TCP-клиентам.

Программа позволяет исследовать, как расположение пожарной станции, параметры распространения огня, работа датчиков и характеристики пожарных групп влияют на ход тушения. Режим `--station-scan` перебирает кандидатов размещения станции и помогает найти наиболее удачную позицию.

## Возможности

- Клеточная карта: трава, деревья, вода и противопожарные рвы.
- Распространение огня с учётом типа растительности, направления и силы ветра, времени горения клетки.
- Датчики, станция и пожарные группы обнаруживают очаги и отправляют сообщения в координационный центр.
- Сообщения могут задерживаться, теряться и дублироваться.
- Координационный центр создаёт задачи и назначает их ближайшим свободным пожарным группам.
- Пожарные группы перемещаются по карте с использованием поиска пути BFS, тушат очаги и могут получать соседние цели без возврата на станцию.
- Цветная отрисовка карты в терминале с поддержкой ANSI.
- Воспроизводимые запуски с фиксированным значением `--seed`.
- Перебор возможных позиций станции с помощью `--station-scan`.
- TCP-сервер событий, встроенный в приложение симуляции.
- Несколько обычных клиентов `fire-client`, независимо получающих ленту событий.
- Несколько комплексных наблюдателей `fire-monitor`, отображающих карту и сводное состояние симуляции.
- Динамическое подключение и отключение клиентов во время работы сервера.
- Уведомление клиентов и закрытие TCP-соединений при завершении симуляции.

## Требования

- Linux.
- Компилятор C: `gcc` или совместимый.
- `make`.
- Терминал с поддержкой ANSI для цветного отображения симуляции.

## Запуск симуляции без сетевого режима

Общий формат:

```bash
./build/fire --map FILE [опции]
```

Основные аргументы:

| Аргумент | Значение |
|---|---|
| `--map FILE` | Файл карты; обязательный аргумент |
| `--conditions FILE` | Файл конфигурации; по умолчанию `data/conditions.conf` |
| `--station R C` | Координаты пожарной станции, индексация с нуля |
| `--station-scan` | Перебрать все позиции станции из секции `station_candidates` карты |
| `--seed N` | Начальное значение генератора случайных чисел для воспроизводимого запуска |
| `--delay MS` | Задержка между тактами в миллисекундах |
| `--quiet` | Не выводить кадры симуляции в терминал; удобно для пакетных запусков |
| `--no-ansi` | Отключить ANSI-раскраску |
| `--listen IP PORT` | Запустить TCP-сервер событий на указанном IP-адресе и порту |

Примеры:

Одиночный прогон:

```bash
./build/fire --map data/map_big_01.map --station 9 15 --delay 200
```

Воспроизводимый прогон:

```bash
./build/fire --map data/map_lake.map --station 7 4 --seed 42 --delay 100
```

Перебор всех кандидатов станции:

```bash
./build/fire --map data/map_big_01.map --station-scan --seed 42
```

Запуск с другим конфигурационным файлом:

```bash
./build/fire --map data/map_lake.map --conditions data/conditions_dry.conf --station-scan --seed 42
```

## Сетевой режим

Сетевой сервер запускается в составе `build/fire`. Для него не требуется отдельный исполняемый файл. Сервер использует TCP и может обслуживать несколько подключённых клиентов одновременно.

### Запуск сервера

В первом терминале:

```bash
./build/fire --map data/map_big_01.map --conditions data/conditions.conf --listen 0.0.0.0 5050 --delay 3000
```

Адрес `0.0.0.0` означает, что сервер принимает подключения на всех сетевых интерфейсах компьютера. Для локальной проверки клиенты подключаются к `127.0.0.1`. Для подключения с другого компьютера вместо `127.0.0.1` указывается IP-адрес машины, на которой запущен сервер. При сетевом запуске также необходимо учитывать настройки межсетевого экрана.

### Обычный клиент `fire-client`

Во втором терминале:

```bash
./build/fire-client 127.0.0.1 5050
```

Обычный клиент получает текстовые события симуляции: сообщения датчиков и групп, действия координационного центра, создание и выполнение задач, изменения состояния пожара и уведомление о завершении сервера. Можно запустить несколько экземпляров клиента в отдельных терминалах.

### Комплексный монитор `fire-monitor`

В третьем терминале:

```bash
./build/fire-monitor 127.0.0.1 5050
```

При подключении монитор отправляет серверу строку регистрации `MONITOR`. После регистрации он получает снимки состояния после каждого такта. На экране отображаются:

- карта с текущим состоянием клеток;
- статистика горящих, безопасных, потушенных и выгоревших клеток;
- позиции и состояния пожарных групп;
- список задач и их состояния;
- сведения о датчиках и сообщениях;
- последние события симуляции.

Можно запускать несколько экземпляров `fire-monitor`. Обычные клиенты получают ленту событий, а снимки состояния предназначены для зарегистрированных мониторов.

### Обозначения карты в мониторе

| Символ | Значение |
|---|---|
| `.` | Трава |
| `t` | Деревья |
| `w` | Вода |
| `_` | Противопожарный ров |
| `F` | Горящая клетка |
| `#` | Выгоревшая клетка |
| `x` | Потушенная клетка |
| `S` | Пожарная станция |
| `s` | Датчик |
| `0–9`, `A–Z` | Пожарная группа |

Если несколько объектов претендуют на отображение одной клетки, монитор показывает обозначение объекта согласно приоритету, заданному текущей моделью отображения.

### Проверка нескольких подключений

1. Запустите сервер командой с `--listen`.
2. В отдельных терминалах запустите два или более `fire-client`.
3. Запустите два или более `fire-monitor`.
4. Убедитесь, что все обычные клиенты получают события, а мониторы обновляют карту и статистику.
5. Закройте один из клиентов и подключите его снова во время симуляции.
6. Дождитесь окончания симуляции и проверьте, что клиенты получают уведомление о завершении и соединения закрываются.

## Управление симуляцией

| Клавиша / действие | Результат |
|---|---|
| `q` | Завершить текущий прогон или весь перебор позиций станции |
| `Ctrl+C` | Прервать выполнение; терминал восстанавливается корректно |

## Результаты симуляции

В ходе работы выводятся номер такта, параметры ветра, количество горящих и потушенных клеток, состояние очередей сообщений, задачи и карта. По завершении печатается итоговая статистика симуляции.

Коды результата:

| Результат | Условие |
|---|---|
| `EXTINGUISHED` | Горящих клеток не осталось |
| `TERRITORY_EXHAUSTED` | Все клетки, способные гореть, выгорели или перестали быть безопасными |
| `TICK_LIMIT` | Достигнуто ограничение `end.max_ticks` |
| `INTERRUPTED` | Симуляция прервана пользователем |

Для режима `--station-scan` выводится результат для каждой проверенной позиции станции, число тактов и показатели распространения/тушения. В конце указывается лучшая позиция по критерию завершения тушения.

## Конфигурационный файл

Файл конфигурации использует формат `ключ = значение`. Строки, начинающиеся с `#`, считаются комментариями.

Основные группы параметров:

| Группа | Параметры |
|---|---|
| Распространение огня | `fire.base_prob_grass`, `fire.base_prob_tree`, `fire.burn_time_factor`, `fire.wind_factor_*`, `fire.spread_8dir`, `fire.reburn_burnt` |
| Ветер | `wind.direction`, `wind.power` |
| Датчики | `sensor.radius`, `sensor.resend_period` |
| Сообщения | `msg.delay_min`, `msg.delay_max`, `msg.loss_prob`, `msg.dup_prob` |
| Пожарные группы | `team.count`, `team.speed`, `team.extinguish_time`, `team.efficiency`, `team.return_to_station`, `team.can_cross_water`, `team.can_cross_firebreak` |
| Завершение | `end.max_ticks`, `end.unlimited` |

Пример конфигурации:

```ini
fire.base_prob_grass       = 0.15
fire.base_prob_tree        = 0.20
fire.burn_time_factor      = 1.5
fire.wind_factor_along     = 1.8
fire.wind_factor_against   = 0.4
fire.wind_factor_side      = 1.0
fire.spread_8dir           = true
fire.reburn_burnt          = false

wind.direction             = SE
wind.power                 = 2

sensor.radius              = 2
sensor.resend_period       = 5

msg.delay_min              = 1
msg.delay_max              = 3
msg.loss_prob               = 0.10
msg.dup_prob                = 0.05

team.count                  = 5
team.speed                  = 2
team.extinguish_time        = 3
team.efficiency              = 1.0
team.return_to_station      = false
team.can_cross_water        = false
team.can_cross_firebreak    = true

end.max_ticks               = 600
end.unlimited               = false
```

Направление ветра задаётся одним из значений: `N`, `NE`, `E`, `SE`, `S`, `SW`, `W`, `NW`.

## Файл карты

Карта содержит секции `size`, `terrain:`, `ignition:`, `sensors:` и `station_candidates:`.

Пример:

```text
size = 16 20

terrain:
w"""""""""""""""""""
w"""ttt""""""ttt""""
...

ignition:
2 5
2 14

sensors:
4 2
4 17

station_candidates:
7 4
7 15
```

Обозначения в секции `terrain`:

| Символ | Значение |
|---|---|
| `"` или пробел | Трава |
| `t` | Дерево |
| `w` | Вода |
| `_` | Противопожарный ров |

Координаты задаются парой `строка столбец`, индексация начинается с нуля. При загрузке карты проверяются размеры строк секции `terrain`, допустимость координат и расположение очагов и кандидатов станции.

## Порядок выполнения одного такта

1. Датчики и пожарные группы наблюдают окружающие клетки.
2. Сообщения передаются с учётом задержек, потерь и дублирования.
3. Координационный центр обрабатывает сообщения и назначает задачи.
4. Пожарные группы перемещаются к целям.
5. Группы выполняют тушение.
6. Огонь распространяется на соседние клетки.
7. Сетевой сервер обрабатывает подключения и публикует события и снимки состояния для мониторов.

## Коды возврата

| Код | Значение |
|---|---|
| `0` | Успешное выполнение |
| `1` | Общая ошибка |
| `2` | Неверные аргументы командной строки |
| `3` | Ошибка конфигурационного файла |
| `4` | Ошибка файла карты |
| `5` | Ошибка инициализации мира |
| `130` | Выполнение прервано через `Ctrl+C` |

## Известные ограничения модели

- При высокой вероятности распространения огня и небольшом количестве пожарных групп огонь может распространяться быстрее, чем группы успевают его тушить. Это допустимое поведение модели.
- Пожарная группа, окружённая огнём или непроходимыми клетками, может не найти путь к цели.
- Результат зависит от карты, конфигурации, начального расположения очагов и значения `--seed`.
- Журнал событий хранится в памяти; отдельный CSV-отчёт в текущей версии не предусмотрен.

### Анализ архитектуры и качества реализации

В ходе анализа были рассмотрены следующие части сетевого взаимодействия:

| Компонент | Что проверялось | Результат анализа |
|---|---|---|
| TCP-сервер (`src/net.c`) | Создание сокета, привязка адреса и порта, приём подключений | Сервер принимает несколько подключений и хранит отдельное состояние для каждого клиента |
| Отправка данных | Частичная отправка, `EINTR`, `EAGAIN` и `EWOULDBLOCK` | Используются очереди отправки и неблокирующий режим, чтобы медленный клиент не останавливал такт симуляции обычной отправкой |
| Обычный клиент (`src/client.c`) | Подключение и чтение потока событий | Клиент получает текстовые события симуляции независимо от других подключённых клиентов |
| Регистрация монитора | Передача команды `MONITOR` | Сервер отличает комплексных наблюдателей от обычных клиентов |
| Снимок состояния | Состав данных и границы снимка | Снимок содержит номер такта, размеры и строки карты, статистику, пожарные группы и задачи; завершение снимка обозначается `@END` |
| Комплексный монитор (`src/monitor.c`) | Приём TCP-потока и разбор строк | Данные накапливаются до символа новой строки, поэтому обработка не зависит от того, как TCP разделил данные на сетевые пакеты |
| Завершение | Уведомление и закрытие соединений | При штатном завершении сервер отправляет уведомление и закрывает клиентские соединения |

Для монитора используется текстовый протокол. Команда `MONITOR` регистрирует специальный тип клиента. Далее сервер передаёт служебные строки `@FRAME`, `@STATS`, `@INFO`, `@MAP`, `@TEAM`, `@TASK` и `@END`. Обычные клиенты продолжают получать текстовую ленту событий, а снимки состояния направляются зарегистрированным мониторам.

### Ошибки, обнаруженные в результате проверки нейросетевого кода

При первой сборке сгенерированного варианта `src/monitor.c` компилятор `gcc` выдал предупреждения. Они были проверены, а соответствующие фрагменты исправлены.

**Ошибка 1. Несоответствие формата `printf` переданным аргументам.**

В функции `draw_frame()` строка формата с двумя спецификаторами `%d` была передана в отдельный вызов `printf` без аргументов. Следующий вызов `printf` получил четыре аргумента, хотя в его строке формата было только два спецификатора. Компилятор сообщил о недостающих аргументах и лишних аргументах.

Причина: строка вывода и аргументы статистики были ошибочно разделены между двумя вызовами.

Исправление: формат и все четыре аргумента объединены в один вызов:

```c
printf("Датчиков: %d | Сообщений в очередях: %d | Доставлено/обработано: %d | Следующий ID: %d\n",
       frame->sensors_count,
       frame->messages_count,
       frame->seen_messages,
       frame->next_message_id);
```

**Ошибка 2. Предупреждение о возможном усечении строки события.**

В функции `add_event()` строка произвольной длины копировалась в элемент массива фиксированного размера `EVENT_SIZE` с помощью `snprintf`. Сам вызов `snprintf` ограничивал запись размером буфера, однако компилятор предупреждал, что исходная строка может оказаться длиннее буфера назначения.

Причина: ограничение длины копируемой строки не было явно указано в формате вывода.

Исправление: максимальная длина копируемой части задаётся явно:

```c
snprintf(events->lines[events->count],
         sizeof(events->lines[events->count]),
         "%.*s",
         EVENT_SIZE - 1,
         line);
```

Длинное событие в таком случае намеренно сокращается до размера буфера с сохранением завершающего нулевого символа. Это предупреждение относилось к возможному усечению текста, а не свидетельствовало о подтверждённом выходе за границы массива.

Обе проблемы были обнаружены не предположительно, а по фактическому выводу компилятора. После внесения исправлений монитор был запущен и проверен вместе с симуляционным сервером и обычным клиентом; отображение состояния симуляции было проверено визуально.

### Ограничения и направления дальнейшей проверки

Проведённая проверка подтверждает базовый сценарий работы сервера, обычного клиента и комплексного монитора. Для более полной проверки следует отдельно выполнить длительный прогон с несколькими мониторами, отключить и повторно подключить одного из них во время симуляции, а также проверить завершение соединений при высокой нагрузке на отправку данных.

В текущей реализации не предусмотрены шифрование TCP-трафика и аутентификация клиентов. Поэтому сетевой режим предназначен для учебной работы и контролируемой среды, а не для передачи данных через недоверенные сети.


### Критическая оценка использования нейросети

Нейросеть ускорила подготовку типового сетевого кода и помогла сформировать структуру комплексного монитора. При этом проверка показала, что автоматически сгенерированный код может содержать ошибки даже в простых операциях вывода. Поэтому результат генерации рассматривался как черновой вариант, требующий компиляции и проверки.

Основные выводы:

- ответы нейросети необходимо сверять с реальными заголовочными файлами, структурами данных и интерфейсами проекта;
- предупреждения компилятора нельзя игнорировать: они могут указывать на ошибки формата, некорректные преобразования типов или потенциальные проблемы с памятью;
- сетевой код необходимо проверять с несколькими подключениями, поскольку успешный запуск одного клиента не доказывает корректность многоклиентской работы;
- работоспособность следует подтверждать практическим запуском сервера и клиентов, а не только анализом текста программы;
- нейросеть не заменяет тестирование и ответственность разработчика за итоговый код.
